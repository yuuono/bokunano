# ブラウザ内Qwenによる操作選択とCNL整形方針

更新日: 2026年10月5日

## 1. 目的

ブラウザ内のQwenが自由な日本語から操作列を選び、検査済みの操作列をCNLへ整形してBoku1-nanoへ渡す。新規指示と、直前の指示に対する追加・変更を同じチャットで扱う。

| 担当 | 役割 |
| --- | --- |
| Qwen | 日本語の意味を判断し、24種類の操作から順序付きで1〜4個を選ぶ |
| JavaScript | 操作名と件数を検査し、選ばれた操作を同じ順序でCNLへ機械的に整形する |
| Boku1-nano | 検査済みCNLからPythonコードを生成する |

JavaScriptは自由文のキーワードから操作を推測しない。入力例も通常のQwen推論を通し、固定コードや正解CNLを返す分岐を設けない。

## 2. 2026年10月5日の変更理由

以前はQwenに完成したCNLを直接生成させていた。チャットの変更依頼で「偶数を残し、2倍する」を「3倍へ変更」と指示した際、手順の書き換え自体は正しくても、CNL文章化の段階で操作が抜けるケースを確認した。

現在はQwenの担当を操作の選択と順序の判断に絞り、検査に通った操作名を定型文へ整形する。意味を選ぶ部分はQwenが担当し、日本語の活用や外側テンプレートは既存の24操作表から決定的に生成する。

学習範囲は最大3操作のまま。Webでは4操作を実験として許可する。4操作のコード生成精度を保証する変更ではない。

## 3. モデルと固定条件

固定値の正は[web/qwen-manifest.json](../../web/qwen-manifest.json)。

| 項目 | 値 |
| --- | --- |
| model | `onnx-community/Qwen3-0.6B-ONNX` |
| revision | `da1453100cf3ff33ef56d17983fc7a8648706db6` |
| dtype / device | q4f16 / WebGPU |
| モデル本体 | 569,789,750 bytes、約543 MiB |
| Transformers.js | 4.3.0 |
| thinking | 無効 |
| 最大生成数 | 192 token |
| 温度 | UIで0〜2、初期値0 |
| T=0 | `do_sample=false` |
| T>0 | `do_sample=true`、指定したtemperature、`top_k=0`、`top_p=1` |
| repetition_penalty | 1.05 |
| 再生成 | 検査失敗時に1回まで、合計2回 |

追加学習は行わない。モデルとJavaScriptの取得通信は発生するが、利用者の入力は外部推論APIへ送信しない。

## 4. Qwenの出力契約

各行に番号と、許可表と完全一致する操作名を出力する。

```text
1. 偶数だけを残す
2. 各要素を3倍する
```

対象外操作、5操作以上、意味が曖昧な依頼には`対応できません。`を返すようプロンプトで指定する。プロンプトによる指示追従は完全ではないため、出力の検査と利用者の解釈確認を行う。

## 5. 検査と整形

[web/cnl.js](../../web/cnl.js)を仕様と実装の正とする。

1. `numberedSteps`が1から連続する番号付きリストであることを検査する。
2. `validateOperationPlan`が1〜4操作であることを検査する。
3. 全操作名を`CNL_OPERATIONS`のlabelと完全一致で照合する。
4. 最後以外はconnective、最後はfinalの表記を使い、読点で連結する。
5. kが必要な操作の有無で外側テンプレートを選ぶ。
6. 生成したCNLを`validateCnl`でも検査する。
7. 4操作には`experimental=true`を付ける。

未知の操作名、欠番、コードや説明の混入は拒否する。同じ操作の反復や、逆に見える並べ替えも、検査器が最適化して削除しない。

外側テンプレート:

```text
整数リストxsから{操作列}solve関数を書いてください。
整数リストxsと整数kを受け取り、{操作列}solve関数を書いてください。
```

CNLを直接編集する場合も、同じ`validateCnl`による検査を通す。

## 6. 会話の引き継ぎ

新規指示は`buildNormalizerMessages`、追加指示は`buildRevisionMessages`でメッセージを作る。追加指示には直前の検査済み操作列と今回の変更依頼を渡し、変更後の全操作をQwenに選ばせる。

前回のCNLを利用者入力の先頭へ単純に埋め込む方法は、前の回答をコピーする誤動作を起こしたため、操作のラベル一覧として渡す。無制限の会話履歴や生成Pythonは送らない。

検査失敗時には前回出力と検査理由を会話へ追加し、1回だけ再生成する。最終的に失敗した場合はBokuへ渡さず、具体的な再入力またはCNL直接編集を案内する。

## 7. UIと実行順序

1. 左Qwenウィンドウで日本語を受け取る。
2. 残っているBokuセッションを解放し、Qwen Workerを起動する。
3. 操作列を生成・検査し、CNLへ整形する。
4. QwenモデルとWorkerを解放する。
5. 同じチャット内に解釈した操作と順序を表示する。
6. 利用者が「この内容でコードを生成」を押す。
7. 右Bokuウィンドウのモデルと温度でコードを生成する。

CNL文法合格は意味の正しさを保証しない。コード生成の完了も実行結果の正しさを保証しない。生成Pythonは自動実行せず、コードとして表示する。

## 8. Bokuの温度と終了条件

T=0はargmax。正の温度では、最大logitを引いてからTで割った値のsoftmaxを計算し、その確率に従って選ぶ。実装は[web/sampling.js](../../web/sampling.js)。

入力と生成を合わせて最大256 tokenとし、EOSなら完了、上限なら未完了の可能性を表示する。停止操作は現在の要求を無効にし、遅れて届いた結果を反映しない。

## 9. 動作環境と検証

QwenはWebGPUを必須とする。BokuはWebGPUを優先し、初期化できない場合にWASMへ切り替える。

- `node --test tests/web/*.test.mjs`でCNL、操作列整形、温度を検査する。
- 同じ検査をPages公開workflowで実行する。
- 実ブラウザでは新規入力、追加指示、4操作、温度変更、停止、モデル切替を確認する。
- 精度が不足する場合も、入力例の固定回答などで補わない。誤解釈を確認・修正できる導線を維持する。

画面の詳細は[チャットUI方針](boku_nano_chat_ui_plan.md)、操作は[Webデモ手順](../procedures/boku_nano_onnx_web_demo.md)を参照。
