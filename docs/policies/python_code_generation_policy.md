# Pythonコード生成器と構造的変種の作成方針

## 目的

意味ASTから、次の固定シグネチャを持つPython関数を機械的に生成する。

```python
def solve(xs: list[int], k: int) -> list[int]:
    ...
```

同じ意味ASTから、意味を変えずに複数のコード表現を生成し、学習データの表面的な偏りを減らす。生成コードはすべて実行検証し、参照インタプリタと同じ結果になったものだけを採用する。

この文書では、コード生成器の責務、参照インタプリタからの独立性、構造的変種、検証方法、保存するメタデータを定める。日本語指示の生成は対象外とする。

操作の分類名と意味ASTのキー名は、[用語統一方針](terminology_policy.md)に従って区別する。

## 入力と出力

入力は、[単独操作の意味AST定義](../specifications/atomic_semantic_asts.md)に従う単独操作、または1〜3個の操作を格納した`sequence`形式の意味ASTとする。

```json
{
  "sequence": [
    {"filter": ["ge_k"]},
    {"map": ["mul_const", 2]},
    {"order": "ascending"}
  ]
}
```

出力は、`solve`関数を1個だけ含むPythonソースコードと、生成に使った構造的変種の情報とする。

```python
def solve(xs: list[int], k: int) -> list[int]:
    values = [x for x in xs if x >= k]
    values = [x * 2 for x in values]
    return sorted(values)
```

生成器は意味ASTの`sequence`を先頭から順番に処理する。操作の並び替え、削除、重複の除去は、意味が同じに見える場合でも通常の生成処理では行わない。

## 参照インタプリタからの独立性

コード生成器と[参照インタプリタ](../specifications/reference_interpreter.md)に同じ誤りが入ることを避けるため、両者を独立した実装にする。

- コード生成器から`reference_interpreter.py`をimportしない
- コード生成器から`interpret`を呼び出さない
- 各操作を実行する関数や条件判定関数を両者で共有しない
- 参照インタプリタの途中結果を使ってコードを組み立てない
- 参照インタプリタは整数リストを直接処理し、コード生成器はPythonの式または文を生成する
- 共有してよいものは、意味ASTの公開仕様、操作名、入力条件などの宣言的な定義に限る

参照インタプリタでは、生成対象外の`itertools.compress`、複数イテラブルを受け取るPython組み込み関数`map`、`heapq.heapify`と`heapq.heappop`、`collections.deque`、`itertools.islice`を使用する。コード生成器は参照側の実装表現に制約されず、この文書で許可した内包表記、`for`ループ、スライス、`sorted`、`reversed`などをすべて生成候補にできる。具体的な分離方針は[参照インタプリタ](../specifications/reference_interpreter.md)で定める。

生成器の正しさは、生成器自身のロジックでは判定しない。別の検証処理が生成コードを実行し、その結果を参照インタプリタの結果と比較する。

## 基本的な生成手順

コード生成は次の順序で行う。

1. 意味ASTの形、操作数、操作名、引数を検証する。
2. 単独操作を、内部では長さ1の操作列として扱う。
3. 使用可能な構造的変種から`style_spec`を決め、正規化した内容から`style_id`を計算する。
4. 操作列を順番にPythonの式または文へ変換する。
5. 固定シグネチャを含む関数全体を組み立てる。
6. `ast.parse`で構文を確認する。
7. 構文の許可リスト、安全性、長さ、シグネチャを確認する。
8. 生成コードを実行し、参照インタプリタと比較する。
9. 検証済みコードだけを保存する。

未知の操作、引数不足、余分なキー、範囲外の定数を見つけた場合は、推測してコードを生成せずエラーにする。

## 各操作のコード化

コード生成器は24個の操作について、参照インタプリタとは別にPython表現を定義する。

### 抽出

抽出は、内包表記または`for`ループで表現する。

| 操作 | 条件式 |
|---|---|
| `even` | `x % 2 == 0` |
| `odd` | `x % 2 != 0` |
| `gt_k` | `x > k` |
| `ge_k` | `x >= k` |
| `lt_k` | `x < k` |
| `le_k` | `x <= k` |
| `multiple_of_k` | `x % k == 0` |
| `positive` | `x > 0` |
| `negative` | `x < 0` |
| `zero` | `x == 0` |

### 変換

変換も、内包表記または`for`ループで表現する。

| 操作 | 要素の式 |
|---|---|
| `add_k` | `x + k` |
| `sub_k` | `x - k` |
| `mul_k` | `x * k` |
| `mul_const, 2` | `x * 2` |
| `mul_const, 3` | `x * 3` |
| `negate` | `-x` |
| `abs` | `abs(x)` |
| `square` | `x * x`または`x ** 2` |

### 並べ替え

| 操作 | 使用できる表現 |
|---|---|
| `ascending` | `sorted(values)`、`sorted(values, reverse=False)` |
| `descending` | `sorted(values, reverse=True)`、`sorted(values)[::-1]` |
| `reverse` | `values[::-1]`、`list(reversed(values))` |

`descending`は値の大小による降順整列であり、`reverse`は現在の並びを反転する操作である。この二つを同じ操作として扱わない。特に、`values[::-1]`だけで`descending`を表現してはいけない。

### 切り出し

| 操作 | 使用できる表現 |
|---|---|
| `take_first_k` | `values[:k]`、`values[0:k]` |
| `take_last_k` | `values[-k:]`、`values[-k::]` |
| `every_other` | `values[::2]`、`values[0::2]` |

`k`は1〜10であるため、`values[-k:]`と`values[-k::]`は、空リストと長さが`k`未満のリストについても期待する意味になる。表に示したすべての表現を参照インタプリタとの比較対象にする。

## コードの構造的変種

### 内包表記と`for`ループ

抽出と変換には、少なくとも次の2形式を用意する。

```python
values = [x for x in values if x % 2 == 0]
```

```python
selected = []
for x in values:
    if x % 2 == 0:
        selected += [x]
values = selected
```

安全性検査で属性アクセスを禁止するため、通常ループでは`selected.append(x)`を使わず、`selected += [x]`を使う。入力`xs`は変更しない。

1つの関数内ですべてを内包表記にする形式、すべてをループにする形式、操作ごとに両者を切り替える混合形式を生成候補にできる。ただし、混合形式は各形式の基本検証が完了してから追加する。

### 一時変数の有無

一時変数を使わない形式では、各操作の式を処理順どおりに入れ子にして、最後に直接`return`する。

```python
def solve(xs: list[int], k: int) -> list[int]:
    return sorted([x * 2 for x in [x for x in xs if x >= k]])
```

一時変数を使う形式では、操作ごとに結果を代入する。1個の変数を再利用する形式と、段階ごとに新しい変数を使う形式を用意する。

```python
def solve(xs: list[int], k: int) -> list[int]:
    filtered = [x for x in xs if x >= k]
    doubled = [x * 2 for x in filtered]
    ordered = sorted(doubled)
    return ordered
```

`for`ループ形式は出力リストを保持する必要があるため、完全な「一時変数なし」の対象にはしない。

### 変数名

[課題文の「コードの構造的変換」](../../boku1-nano.md#コードの構造的変換)では、変数名を変更したコードも作ることだけが決められており、使用する名前や候補数は指定されていない。次の名前はコード生成器で使用できる候補例であり、確定した許可リストではない。

- 処理中のリスト: `values`、`items`、`result`、`current`
- 新しいリスト: `selected`、`mapped`、`output`、`next_values`
- 要素: `x`、`value`、`item`、`number`

実装前に、各役割で実際に採用する名前と候補数を決める。候補を決める場合も、Pythonの予約語、組み込み関数名、`xs`、`k`との衝突、同じスコープで意味が曖昧になる重複は許可しない。意味ASTや日本語指示に含まれる文字列を、そのまま識別子として埋め込まない。

### 条件式の向き

[課題文の「条件式の順序変更」](../../boku1-nano.md#コードの構造的変換)は、抽出条件にある比較式の左右を入れ替え、同じ意味を保つ表現を生成するものとする。

```python
x > k
k < x
```

```python
x % 2 == 0
0 == x % 2
```

現在の単独操作ASTでは1操作につき条件が1個だけなので、変更するのはその比較式の書き方だけである。意味ASTに並んでいる操作の順序や、複数の抽出操作を適用する順序は変更しない。左右を入れ替えた表現も、ほかの変種と同様に参照インタプリタとの比較を必須とする。

### 1行形式と複数行形式

「1行形式」は、関数本体を1個の`return`文で表す形式とする。`def`文まで物理的な1行に詰め込む形式は生成しない。

「複数行形式」は、各操作を代入文またはループとして順番に記述し、最後に`return`する。意味ASTの操作順をコード上でも追跡しやすいため、生成器の初期実装では複数行形式を基準とする。

### コメント

コメントは承認済みの短い定型文だけを使用し、意味を追加または変更しない。

```python
# k以上の値だけを残す
# 各要素を2倍する
# 昇順に並べる
```

コメントの変種は、次の2択だけとする。

- `none`: コメントなし
- `present`: コメントあり

「関数全体を説明するコメント」と「各段階を説明するコメント」を別々の変種として数えない。コメントありのコードでは、生成コードが実際に行う処理だけを定型文で記述する。コメント内に、コードが実行していない処理を書いてはいけない。

### 型注釈

課題の固定シグネチャを守るため、`solve`の引数と戻り値の型注釈は常に残す。型注釈の有無による変種は、ローカル変数だけを対象にする。

```python
result: list[int] = []
```

これにより、型注釈の表現差を含めながら、すべての生成コードを同じ公開インターフェースで呼び出せる。

### 降順と逆順の表現

降順には次の2形式を用意する。

```python
sorted(values, reverse=True)
sorted(values)[::-1]
```

現在の並びの反転には次の2形式を用意する。

```python
values[::-1]
list(reversed(values))
```

`ascending`の直後の`reverse`を`sorted(..., reverse=True)`へまとめるような操作間の書き換えは、基本生成器には入れない。後から追加する場合は、書き換え規則を個別に列挙し、通常の逐次形式とは別の`rewrite_id`を付け、参照インタプリタとの比較を必須とする。

## 1つの意味ASTから得られるコード候補数の概算

構造的変種を実装するときの規模を把握するため、1操作の意味ASTから生成できるコード候補数を概算する。この概算は生成可能な候補数の目安であり、訓練データへ採用する件数や、1意味AST当たりの上限ではない。

ここでは次の記号を使う。

- `E`: 要素変数名の候補数
- `R`: 結果を保持するローカルリスト変数名の候補数
- 比較式の左右入れ替え: 2通り
- コメント: なし・ありの2通り
- ローカル型注釈: なし・ありの2通り

変数名の候補数はまだ確定していないため、`E`と`R`を固定値にはしない。2種類、3種類、4種類とした場合の目安を併記する。

| 1操作の意味AST | 概算式 | `E=R=2` | `E=R=3` | `E=R=4` |
|---|---:|---:|---:|---:|
| 抽出の各操作 | `4E + 16ER` | 72 | 156 | 272 |
| 二乗以外の変換の各操作 | `2E + 8ER` | 36 | 78 | 136 |
| 二乗 | `4E + 16ER` | 72 | 156 | 272 |
| 昇順 | `4 + 8R` | 20 | 28 | 36 |
| 降順 | `4 + 8R` | 20 | 28 | 36 |
| 現在順の反転 | `4 + 8R` | 20 | 28 | 36 |
| 切り出しの各操作 | `4 + 8R` | 20 | 28 | 36 |

抽出の`4E + 16ER`は、次のように数える。

- 直接`return`する内包表記: 要素変数`E` × 比較式の向き2 × コメント2 = `4E`
- 複数行の内包表記: 要素変数`E` × 結果変数`R` × 比較式の向き2 × コメント2 × ローカル型注釈2 = `8ER`
- `for`ループ: 要素変数`E` × 結果変数`R` × 比較式の向き2 × コメント2 × ローカル型注釈2 = `8ER`

変換では比較式の左右入れ替えを使わないため、通常は抽出の半分になる。二乗だけは`x * x`と`x ** 2`の2表現があるため、抽出と同じ候補数になる。昇順、降順、現在順の反転、各切り出しも、それぞれ2種類の実装表現を使う。

この表は、各変種を独立に組み合わせた生成前の概算である。実際の候補数は、変数名の衝突、両立しない形式、構文・安全性検査、参照インタプリタとの不一致、完全重複の除外によって減る。2操作・3操作の意味ASTでは、コメントやレイアウトなど関数全体で共有する変種があるため、この表の件数を単純に掛け合わせない。実際に列挙した後の`candidate_count`、`verified_count`、`deduplicated_count`を記録する。

## 訓練データの選抜基準

コード生成器が作れる候補の総数は、訓練データの採用基準にしない。[課題文の「データの検証と選抜」](../../boku1-nano.md#データの検証と選抜)に従い、検証を通過した候補から次の分布を均等に近づける。

- 操作数1、2、3
- 各演算子の出現頻度
- コード形式
- 日本語テンプレート
- 1つの意味ASTから採用する最終レコードに上限を設ける

コード生成器の役割は、均等抽出に使用できる構造的変種を生成するところまでとする。実際の採用処理は、コードと日本語指示を結合した最終レコードを対象に行う。具体的な選抜方法は[訓練データの均等選抜](data_record_policy.md#訓練データの均等選抜)で定める。

## 変種の組み合わせ方

すべての変種の直積を生成すると、複雑なASTほど組み合わせ数が急増する一方、単純なASTでは相異なる候補が少なくなる。そのため、次の方式を採用する。

1. 各変種を構造化した`style_spec`として表す。
2. 意味ASTと両立する候補だけを上限付きで列挙する。
3. 正規化した`style_spec`から`style_id`を計算する。
4. 意味ASTからその場で計算した`semantic_hash`、`style_id`、固定seedから候補を決定的に順位付けする。
5. Pythonコードを生成し、構文・安全性・実行結果を検証する。
6. 完全重複コードを除外する。
7. 全体で各コード形式の出現数を集計し、偏りが大きい形式を間引く。

同じ入力とseedからは、実行のたびに同じコードが生成されるようにする。ランダム選択を使う場合も、グローバルな乱数状態には依存しない。

1つの意味ASTから採用する最終レコード数の上限はコード生成器では決めない。コードと日本語指示を結合した後の選抜処理で、設定された上限を適用する。

`style_spec`の例を次に示す。

```json
{
  "collection_form": "for_loop",
  "temporary_form": "fresh_names",
  "name_set": "descriptive",
  "layout": "multi_statement",
  "comments": "present",
  "local_annotations": true,
  "descending_form": "reverse_keyword",
  "reverse_form": "slice_notation"
}
```

この正規化JSONから`style_id`を計算する。`style_id`自身を`style_spec`へ含めない。単一の`code_style`文字列だけに全情報を詰め込まず、集計可能な個別フィールドとして保持する。

## 構文と安全性の制限

生成コードは、固定テンプレートと許可済みの演算子だけから組み立てる。その上でPython ASTを調べ、少なくとも次を確認する。

- トップレベルには`solve`関数が1個だけ存在する
- 引数が`xs`と`k`の2個で、固定の型注釈と戻り値注釈を持つ
- `import`、属性アクセス、ラムダ、クラス、追加関数、`while`、例外処理を含まない
- `eval`、`exec`、`open`、動的な組み込み関数参照を含まない
- 呼び出せる関数を`sorted`、`abs`、`reversed`、`list`に限定する
- 定数は意味ASTとテンプレートが要求する整数、文字列、`True`、`False`、`None`に限定する
- `xs`へ代入せず、入力リストを変更しない
- 生成コードの文字数またはトークン数が設定した上限以内である

実行時の名前空間も必要最小限にし、許可した組み込みだけを渡す。ただし、名前空間の制限だけを安全性の根拠にせず、実行前のPython AST検査を必須とする。

## 実行検証

構文検査を通過した各コードについて、別の検証プログラムが次を確認する。

1. 制限時間内にコンパイルと実行が完了する。
2. `solve`を指定した`xs`と`k`で呼び出せる。
3. 戻り値が整数だけを含む`list`である。
4. 呼び出し後も入力`xs`が変更されていない。
5. 参照インタプリタの戻り値と完全一致する。

検証入力には、空リスト・1要素・負数・ゼロ・重複値・`k`の境界値などと、固定seedで作るランダム入力を含める。すべての期待結果は参照インタプリタから得て、人手で操作別の期待値を別途定義しない。1件でも不一致、例外、時間超過があれば、そのコードは採用しない。

生成コードの完全重複は、[生成コードの完全重複を訓練データから除外する方針](code_duplicate_exclusion_policy.md)に従って、実行検証後に除外する。

## 保存するデータ

生成した各コードについて、少なくとも次を保存する。コード生成候補と、日本語指示を結合した最終学習レコードは別の段階として管理する。完全なスキーマ、ID、`null`の扱い、出力ファイルは[データレコードの作成・管理方針](data_record_policy.md)に従う。

```json
{
  "code_id": "code-...",
  "spec_id": "combined-000001",
  "semantic_ast": {},
  "reference_code": "def solve(...):\n    ...",
  "code_style": "staged_loop",
  "style_id": "style-...",
  "style_spec": {},
  "split": "train",
  "test_suite": null,
  "generator_version": "...",
  "generator_seed": 0,
  "semantic_hash": "...",
  "code_hash": "...",
  "verification": {
    "syntax_ok": true,
    "ast_safe": true,
    "signature_ok": true,
    "tests_passed": true,
    "input_unchanged": true,
    "timeout": false
  }
}
```

`code_hash`は、保存する`reference_code`のUTF-8バイト列に対するSHA-256とする。完全重複の最終判定では、ハッシュだけでなくコード文字列全体も比較する。

日本語指示を結合した最終レコードでは、`instruction_ja`、`tests`、`difficulty`、`text_hash`、教師モデル関係の項目を追加する。教師モデルを使用しないレコードでも、`teacher_model`、`teacher_revision`、`prompt_hash`は省略せず`null`として保存する。

## 正式生成前の設定

1操作ASTごとに検証済み固有コードを20件確保する次の実行で使う設定は、[`config/python_code_generation.json`](../../config/python_code_generation.json)に固定する。この設定には、入出力ファイル、対象操作数、1 AST当たりの目標数、変数名、seed、長さ上限、検証入力数、時間制限、完全重複の判定方法、Python環境を保存する。

このJSONは正式生成用であり、24操作を1件ずつ確認した既存の実行結果とは分けて管理する。2026年9月20日にこの設定を読み込んで単一操作ASTごと20件を生成した。結果は[単一操作のPythonコード候補生成結果](../results/single_operation_python_code_generation_results.md)に記録する。

2操作・3操作についても、2026年9月20日に1意味AST当たり20件を生成した。訓練用と組合せ汎化テスト用、2操作と3操作をそれぞれ別の設定JSONに固定した。生成順は、組合せ汎化2操作、組合せ汎化3操作、訓練2操作、訓練3操作とする。後から生成する集合は、それ以前に生成した比較対象のコードJSONLを`exclude_code_jsonl`へ指定する。結果は[2操作・3操作のPythonコード候補生成結果](../results/multi_operation_python_code_generation_results.md)に記録する。

検証、通常テスト、反復汎化についても、2操作と3操作を別の設定JSONに固定し、同日に1意味AST当たり20件を生成した。結果は[検証・通常テスト・反復汎化のPythonコード候補生成結果](../results/evaluation_python_code_generation_results.md)に記録する。

設定の項目、Pythonバージョン、ロックファイル、入力ファイルを検査する場合は、次を実行する。このコマンドはコード候補を生成しない。

```bash
uv run python scripts/code_generation/generate_python_code_candidates.py \
  --config config/python_code_generation.json \
  --validate-config
```

正式生成では次を実行する。生成条件の個別引数は`--config`と併用できず、JSONの値だけを使う。

```bash
uv run python scripts/code_generation/generate_python_code_candidates.py \
  --config config/python_code_generation.json
```

24操作を1件ずつ生成した予備確認は、設定JSONの接続前に必要な生成条件をコマンド引数で個別に渡して実行した。目標数は正式生成の20件ではなく1件であり、実際に使った値は`data/code_candidates/atomic_preview/atomic_python_code_generation_stats.json`に保存してある。そのため、24件の検証結果は「各24操作から1件の正しいコードを生成できた」ことの予備確認として有効である。

## 実装の進め方

最初に、24個の1操作ASTを1つずつ処理する。

1. 1操作ASTから`style_spec`を決定的な順序で列挙する。
2. 各`style_spec`からPythonコードを生成する。
3. 構文、安全性、シグネチャ、長さを検査する。
4. 生成コードを実行し、参照インタプリタと全検証入力で比較する。
5. 完全重複コードを除外する。
6. 固有な検証済みコードが20件へ到達するまで、次の`style_spec`を処理する。
7. 候補を使い切っても20件へ届かなければ、操作名、採用件数、不採用理由を記録する。
8. 24個すべての1操作ASTを確認してから、2操作・3操作ASTの生成へ進む。

ここでの20件は、1〜3操作ASTについて生成器の能力を確認するための目標件数であり、最終訓練データにおける1意味AST当たりの採用上限ではない。構造的変種の種類にかかわらず、生成したコードはすべて同じ検証手順を通し、参照インタプリタと一致したものだけを採用する。

## 完了条件

コード生成器は、次をすべて満たした時点で完成とする。

- 24個の単独操作をすべて生成できる
- 1〜3操作の意味ASTについて、操作順を保ったコードを生成できる
- 参照インタプリタの実装をimportまたは再利用していない
- 規定した各構造的変種を少なくとも1件生成できる
- 同じseedから同じコードを再生成できる
- 全生成コードが構文、安全性、シグネチャ、時間、入力不変性の検査を通る
- 全検証入力で参照インタプリタと一致する
- 形式別の生成件数と不採用理由を集計できる
- 完全重複除外後に、訓練コードと組合せ汎化テスト正解コードの積集合が空である
