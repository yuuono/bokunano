# Boku1-nano WebデモのチャットUI刷新方針

作成日: 2026年10月5日

状態: 現行UIは「21. チャット内入力と時系列表示」を適用する。白背景を維持し、入力欄はチャット内、最新のやり取りは下に配置する。過去の方針と検証記録は変更履歴として残す。

## 1. 目的

段階別フォームを、会話履歴と入力欄を中心にしたチャットへ変更する。Qwenの対話ウィンドウとBoku1-nanoのコードウィンドウを左右に分ける。自由な日本語の入力、Qwenによる書き換え、解釈の確認、コード生成、追加の修正を一つのチャット内で完結させる。

見た目を重要な成果物として扱い、画面全体の余白、文字、会話の幅、入力欄、コード表示を一体で設計する。発表時には、初めて見た人が「指示を入力し、解釈を確かめ、コードを得る」という流れを把握できることを目標とする。

本書では画面と操作の変更を計画する。新しいモデルの学習や対応操作の拡張は含めない。

## 3. 見た目の設計

### 画面構成

デスクトップでは左にQwen、右にBoku1-nanoを配置する。スマートフォンなどの狭い画面は縦に並べる。両ウィンドウにモデルの状態と独立した温度設定を置く。

- 上部: Boku1-nanoの名前、現在のモデル、設定を開く操作。
- 左端: ブランド表示と「新しい会話」の細いナビゲーション。会話一覧の永続保存は今回含めない。
- 中央左: Qwenとの会話履歴、解釈した操作、生成確認、入力欄。中央右: Boku1-nanoのモデル設定とコード生成履歴。
- 下部: 複数行の入力欄、送信、処理中の停止。入力欄は会話の最下部から常に操作できる。
- 初期画面: 短い使い方と、クリックすると入力欄へ入る数個の例。

### 初期のデザイン基準

- 濃いネイビーを基調に、Qwenはラベンダー、Boku1-nanoはミントをアクセントにする。細い境界線、丸み、整った余白で2つのモデルの役割を分ける。
- 2ペインで会話とコードを同時に読める幅を確保し、文字と余白は実画面で調整する。本文・入力・操作一覧は18px、コードは16px、補助情報は13px以上とし、コードは領域内で横スクロールする。
- 利用者の入力とモデルの回答を、配置と背景の差で区別する。
- コードは等幅フォント、行間、コピー操作を用意し、長い行はコード領域内で横スクロールする。
- モデル名や待機状態は補助情報として表示し、主要な操作を圧迫しない。
- 色だけで成功・失敗を伝えず、短い日本語を添える。
- ChatGPT型の操作構成を参考にしつつ、製品名と説明はBoku1-nanoとして表示する。

### 詳細情報の置き場所

CNLの全文、操作一覧、Qwenへ渡すプロンプト、backend、token数などはメッセージの詳細や設定へ配置する。通常の会話では「どの処理と解釈したか」「生成結果は何か」を優先する。

## 4. 基本の会話フロー

### 初回の指示

1. 利用者が「偶数だけ残して、2倍して」と送信する。
2. 利用者の発言を会話へ追加する。
3. Qwenの初回取得・読込・解釈中という現在の状態を表示する。
4. Qwen出力を既存のCNL検査器で検査する。
5. 「偶数を残し、その後で2倍します」という解釈と操作順を表示する。
6. 同じメッセージ内に「この内容で生成」と「修正」を表示する。
7. 確認後、Boku1-nanoがコードを生成し、同じ会話に回答として表示する。

処理の説明はQwenが生成した検査済みCNLや既存の操作ラベルから表示する。入力例に対して固定のコードを返す特別処理は作らない。

### 追加の修正

続けて「最後に逆順にして」と入力された場合、Qwenに直前の検査済み指示と新しい依頼を渡す。Qwenは変更後の全手順を許可表の操作名で出力する。JavaScriptが操作名と件数を検査し、選ばれた操作の順序を保って完全なCNLへ整形する。整形後に再度解釈確認へ進める。

Boku1-nanoへ会話履歴全体を入力する設計にはしない。毎回、Qwenが整理した単独で意味の通るCNLを渡す。これにより、現在の学習形式と系列長上限に合わせる。

### 新しい会話

「新しい会話」で確定済み指示、途中の解釈、会話履歴を新規状態へ切り替える。前の会話に対する遅れて到着した推論結果が新しい会話に混ざらないよう、会話IDと要求IDで照合する。

## 5. 会話の意味と文脈の管理

### 保持する情報

| 情報 | 用途 |
| --- | --- |
| 会話ID、発言ID、要求ID | 結果と対象の発言を対応させる |
| 元の日本語入力 | 利用者の意図を表示・追跡する |
| 最後に確定したCNL・kの値 | 次の追加指示の基準とする |
| 検査済み操作列 | 解釈の表示と意味比較 |
| 確認前のCNL候補 | 修正待ちの状態を保持する |
| 使用モデルID・tokenizer ID | 各コード回答の生成条件を保持する |
| 生成コードと終了理由 | 完了・中止・打ち切りを区別する |

### 追加指示のルール

- 「最後に〜」「それを〜」は、直前に確定した操作列を基準にする。
- 確認前の解釈を修正している場合は、その候補を修正対象として明示してQwenへ渡す。
- 新規依頼か既存指示への変更かが曖昧な場合は、勝手に処理を足さず、同じチャット内で短く確認する。
- Qwenに渡す文脈は、必要な直前状態と今回の依頼に絞る。長い会話を無制限に送らない。
- 確認済みCNLは、利用者が新しい解釈を確定するまで上書きしない。
- JavaScriptはQwenの操作名の検査、CNLへの機械的な整形、表示を担当する。自由文の意味を独自のキーワード規則で書き換えない。

Qwenの応答は「許可表の操作名を並べた番号付きリスト（具体的な整数は末尾にk=整数を追加）、または対応できません」とする。曖昧な場合は会話内で具体的な指示への修正を案内する。CNL本文はJavaScriptで操作名から機械的に整形し、上限を4とする。

## 6. 機能の範囲

### 今回の必須機能

- 会話形式での自由文入力とコード表示。
- Qwenの解釈を同じチャット内で確認・修正する機能。
- 前回の指示に対する追加・変更。
- 既存8モデルの選択と、回答ごとの使用モデル表示。
- 最大4操作のCNL検査とコード生成。
- QwenとBoku1-nanoで独立した温度スライダー（0〜2、0.1刻み、初期値0）。
- モデル取得・読込・変換・生成の状態表示。
- 処理の停止、コードのコピー、新しい会話。
- 対応外入力やWebGPU非対応時の説明。
- CNL直接入力・編集を詳細操作として残す。
- キーボード操作と狭い画面への対応。

発表用の初期選択は15M・1 epoch・既存BPEを基本とする。既存の3 epoch・10 epochモデルも選べるようにし、初期値を変更した場合は説明文と手順書も合わせる。

### 後続の拡張候補

- 同一指示をQwen単体でもコード生成させる比較操作。
- 保存済みベンチマーク結果を会話から開く表示。
- トークンごとの確率を観察する学習用モード。温度設定自体は今回の必須機能として実装する。
- ブラウザ再起動後も残る会話履歴。

初期実装の履歴はページ内で保持する。永続保存を追加する場合は、保存先と削除操作を仕様化する。比較機能ではQwen単体とQwen＋Bokuの経路を明示する。

## 7. 状態管理とモデルの実行

基本状態は次の順で遷移する。

`入力待ち → Qwen読込 → 解釈生成 → CNL検査 → 利用者確認 → Boku読込 → コード生成 → 完了`

各処理から中止・失敗状態へ遷移できるようにする。解釈生成の再試行は既存の最大2回を基本とする。

- 同じ会話で複数の生成処理を同時に走らせない。
- 各実行に固有のjobオブジェクトを割り当て、現在のjobとの一致で古い結果を破棄する。処理中の会話切替は無効にする。
- Qwenの処理後はWorkerとモデルを解放してからBokuを動かす。
- 2回目以降の会話では、残っているBokuセッションも確認し、Qwen読込前に必要な解放を行う。
- モデル切替中・推論中の選択操作を制御し、表示モデルと実際のモデルを一致させる。
- コピー操作は表示済みコード本文を対象にし、途中で中止したコードには未完了の表示を付ける。
- ユーザーが過去の発言を読んでいる間は、生成のたびに最下部へ強制移動しない。
- 生成コードは表示のみとする。ここで「4操作の実行」は4操作の指示によるモデル推論を指す。生成Pythonの自動実行は含めない。

初回のQwen取得は約543 MiBである。取得進捗と推論中の表示を区別し、処理が止まっているように見える状態を避ける。

## 8. エラー・対応外入力の扱い

| 状況 | 表示と操作 |
| --- | --- |
| 未対応操作・5操作以上 | 対応範囲を短く説明し、入力の修正を促す |
| 指示が曖昧 | 何を確認するかを同じ会話に表示 |
| CNL検査失敗 | 再試行後も失敗したら理由と修正操作を表示 |
| 意味の誤解釈 | 「修正」または追加発言で再解釈 |
| モデル取得失敗 | 再試行できる操作を表示 |
| WebGPU非対応 | Qwenが使えないことを示し、CNL直接入力を案内 |
| BokuのWebGPU初期化失敗 | 既存のWASM切替を維持し、実行方式を詳細に表示 |
| 生成上限到達 | 完成した回答と区別して打ち切りを表示 |
| 中止 | 未完了表示を残し、次の入力を受け付ける |

QwenのCNL文法合格は意味の正しさを保証しない。このため、通常操作でも解釈と順序を確認できるようにする。

## 13. 追加要望による確定仕様

### 4操作の扱い

- 24種類の語彙と操作の意味は変更せず、CNL検査・Qwenのプロンプト・UIの上限を4操作へそろえる。
- モデルの学習範囲は最大3操作のまま。4操作は対応精度を保証しない実験として、確認欄と生成コード欄へ表示する。
- 4操作を3操作へ削ったり、固定コードへ置き換えたりしない。モデルが実際に生成した結果を表示する。
- 5操作以上、未知の操作、不正なkのテンプレートは従来と同じ検査経路で拒否する。
- Bokuの生成は入力と出力を合わせて最大256 token。EOSまで生成し、上限時は「長さ上限・未完了」と明示する。

### 温度

- QwenとBokuにそれぞれ0〜2の設定を置く。0はgreedy、正値はtemperature sampling。
- Bokuは最大logitを引いてからTで割り、softmaxの確率で抽選する。top-k/top-pによる追加の候補制限は行わない。
- QwenはTransformers.jsのdo_sampleとtemperatureへ接続する。正値時はtop_k=0、top_p=1を指定する。既存のrepetition_penalty=1.05は維持する。
- Qwenは1〜4操作を出力できる余裕を持たせ、各生成を最大192 token、操作列の再生成は1回までとする。追加指示でも変更後の全操作を一度に選ばせる。
- 実行中の温度変更は無効にする。各回答に実際の温度を記録し、後で設定を変えても過去回答の条件を変えない。
- 温度を上げると正解率が上がるとは説明しない。既存のベンチマークや学習結果も書き換えない。

### 公開

実機確認後、今回の変更ファイルを明示してcommitし、mainへpushする。Pages公開workflowの対象commitと成功状態を確認し、公開ページのHTML・JS・CSSがローカルと一致すること、および公開UIで実際に推論できることまで確認する。

## 2026-10-05 v11：生成コードと参照インタプリタの実行比較

利用者の追加要望により、以前の「表示のみ」の範囲を広げる。自動実行はせず、各コードカードの末尾にxs・kの入力欄、「別の入力例」「実行して参照結果と比較」を置く。結果は参照値・生成Pythonの値を並べ、一致、不一致、生成コードのエラー、参照側のエラーを区別する。一致はその入力についての確認であり、全入力の正しさを意味しない。

- 生成開始時に検査済みCNLの操作IDから、データセットと同形式の意味ASTを保存する。単独操作は原子AST、2〜4操作はsequence。順序と重複を保存し、凍結する。生成Pythonから正解ASTを逆算しない。
- 各検証欄はそのカードのコード・意味ASTを複製して保持する。現在のCNL、モデル、別カードの結果を変更しても比較対象を変えない。ASTは詳細から閲覧可能。
- リポジトリのreference_interpreter.pyをそのままWebへ同梱する。テストで元ファイルとの完全一致を検査する。通常の1〜3操作はinterpretを直接使用し、4操作はWeb側のアダプタで入力検査後、同じ操作ハンドラを順に適用する。学習・評価用の参照仕様は変更しない。
- xsは−100〜100の整数を最大20個、空リストも可。kは1〜10。数値が指示で指定されていれば入力欄の初期値にし、試験時は入力したkを両方へ明示的に渡す。関数のデフォルト値は書き換えない。
- PythonはPyodide 0.29.2を必要時に読み込み、実行ごとに独立したWorkerを作成する。実行終了・停止・タイムアウトで破棄し、別コードへの状態の混入を防ぐ。新しい会話でも検証を停止する。同時に走る検証は1つまで。
- 生成コードはsolve(xs, k)関数1つとリスト処理の構文に限定し、import、属性アクセス、任意関数呼び出し、再帰などは実行前に拒否する。実行ステップ数と時間に上限を設ける。エラーの場合も参照結果を残す。生成途中で止まったコードにも未完了を明示して検証欄を付ける。
- Python整数で比較し、大きな整数をJavaScript数値に変換しない。結果表示には文字列を使う。入力を編集した時点で古い一致表示を消す。

実行環境の構成は[Pyodide公式のWorker手順](https://pyodide.org/en/0.29.2/usage/webworker.html)に基づく。初回はモデルに加えPython実行環境の取得通信が発生するが、入力や生成コードを外部の推論・実行APIへ送らない。
