# Boku1-nanoとブラウザ版Qwenの100問比較ベンチマーク作成方針

作成日: 2026年10月5日

更新内容: 承認済み日本語表現辞書の参照を維持し、利用者の指定により比較対象を条件A・Bに絞った。[条件Aの不合格例](../results/browser_100/dev50_20261005_condition_a_failures.md)を追加。

状態: 開発用50問（10分類×5問）の作問・ブラウザ推論・採点を2026年10月5日に実施。[実測結果](../results/browser_100/dev50_20261005_results.md)と[全問のプロンプト・出力](../results/browser_100/dev50_20261005_details.md)を保存。本番100問は未作成・未評価。

## 1. 目的と発表資料での位置付け

対象分野を限定して学習したBoku1-nanoと、ブラウザで動作する汎用小型モデルQwenを、同じコード生成課題で比較する。比較対象は整数リストに対する24操作、最大3操作の組み合わせに限定する。

2026年10月2日に確認された発表資料は、[boku1_nano_presentation_loss_attention_marp.pptx](../report/boku1_nano_presentation_loss_attention_marp.pptx)。既存34枚の内容を保ち、ベンチマークの設計、総合結果、分類別結果の3枚を追加する。既存の18枚目「全体が高精度でも、言い換えには弱い」の後を挿入候補とする。

検証する仮説は「ブラウザで動作する規模のモデルでは、対象分野に特化した小さなモデルが、より大きい汎用モデルを上回る場合がある」。優位性は実測後に判断し、上回らなかった場合も結果をそのまま示す。

## 3. 70点という目標の扱い

70点は「得意な問題だけでは満点に近くなり、難問だけでは能力が見えなくなることを避けるための難易度目安」とする。

1. 開発用として各分類5問程度、合計50問程度の候補を別途用意する。
2. Boku1-nanoの直接生成を評価し、70点前後を想定できる問題構成を検討する。暫定目安は65〜75%とする。
3. 調整対象は文の長さ、表現の自然さ、操作数、分類内の難易度配分とする。承認済み辞書に基づく表現と、Astraによる新規表現の比率も開発段階で決めて記録する。分類ごと10問という本番構成は維持し、意味の曖昧さや未承認表現の混入によって難易度を上げない。
4. 難易度方針を確定後、新しい本番100問を作成・検証して固定する。
5. 本番では問題、モデル、プロンプト、採点条件を変えずに両モデルを測定する。

本番が70点ちょうどになる保証はしない。たとえば63点や78点であっても実測値を示す。開発段階でBoku1-nanoの成績を見て難易度を調整した事実を報告する。この100問は対象分野の比較用評価であり、汎用プログラミング能力全体の代表標本とは扱わない。

## 4. 10分類×10問の構成

| ID | 分類 | 出題内容 | 主な確認点 |
| --- | --- | --- | --- |
| C01 | 基本的な抽出 | 偶数、奇数、正、負、ゼロ | 条件を正しく選ぶ |
| C02 | kを使う条件 | kより大きい、以上、未満、以下、倍数 | 比較演算子の区別 |
| C03 | 値の変換 | 加減算、k倍、2倍、3倍、符号反転、絶対値、二乗 | 数値操作の選択 |
| C04 | 順序の変更 | 昇順、降順、現在順序の反転 | ソートと反転の区別 |
| C05 | 切り出し | 先頭k個、末尾k個、先頭から1個おき | 位置・範囲の解釈 |
| C06 | 2操作の合成 | 異なる2操作 | 操作の漏れと順序 |
| C07 | 3操作の合成 | 異なる3操作 | 複数段階の指示追従 |
| C08 | 同じ操作の反復 | 同じ操作を2回または3回 | 回数と効果の保持 |
| C09 | 順序を取り違えやすい合成 | 抽出と変換、切り出しと整列など | 順序を逆にすると結果が変わること |
| C10 | 未学習の言い回し | 冒頭変更、丁寧表現、自然な言い換え | 操作内容を保った表現変化への対応 |

### 分類の重複と難易度

- 主分類は作問時に一つだけ付ける。C10、C09、C08として設計した問題はC01〜C07へ重複計上しない。
- 操作数、含まれる操作、表現の種類、難易度は別の補助タグで記録する。
- 1操作しか扱わない分類では意味ASTが同じになる問題もある。文章の重複は除き、意味ASTの重複数は報告する。100問すべてが異なる意味を持つとは説明しない。
- C09には、操作順を入れ替えた誤答を実際に区別できるテスト入力を必ず含める。
- C08では2倍や加算など、回数の違いが出力に現れる問題を中心にする。冗長な反復だけで構成しない。
- C10以外にも読みやすい日本語を用いるが、表現変化そのものを主眼とする問題はC10へ置く。
- 意味が曖昧な省略、未対応操作、4操作以上は本番得点の対象に含めない。それらはUIの別の動作確認で扱う。

## 5. Astraへの問題作成依頼

実作業に進む際、Astraへ次の情報を渡して作問を依頼する。この方針書の作成段階では依頼を実行しない。

### 承認済み日本語表現辞書を基準にする

利用者が最終承認した表現を、操作の意味と自然な日本語の基準にする。Astraが自由に作った表現だけで100問を構成しない。参照元は次の公開済みファイルとし、作問時点のファイルSHA-256とGitコミットを固定する。

| 資料 | 用途 |
| --- | --- |
| [承認済み日本語表現辞書CSV](../../data/instruction_dictionaries/release/japanese_atomic_expressions.csv) | `expression_ja`と`connective_expression_ja`を最終承認表現として参照。`operation_id`、`operation_ast`、`canonical_meaning_ja`、`must_preserve_ja`で意味を確認する |
| [表現の生成・修正来歴](../../data/instruction_dictionaries/release/japanese_atomic_expression_provenance.jsonl) | `expression_id`でCSVへ対応付け、承認後の表現と修正前候補を区別する。作問の本文にはCSVの最終表現を使う |
| [train・test_onlyの分割設定](../../config/build_approved_expression_dictionary.json) | 人手選定済みの23件を識別し、Astraへ渡してよい522件を抽出する |
| [日本語言い換えテスト方針](japanese_paraphrase_test_policy.md) | 既存テスト専用表現の隔離、旧表記2件の除外、辞書外9件の扱いを維持する |
| [辞書外の人手追加9表現](../../data/instruction_dictionaries/release/paraphrase_test_external_expressions.jsonl) | 既存テスト専用表現への一致を検査するために使う。承認済み545件の辞書に混ぜない |

現在の辞書は545件で、`train=522`、`test_only=23`。CSV自体に分割列はないため、分割設定の`test_only_expression_ids`と結合して区分を確定する。件数やID、CSVと来歴の最終表現が一致しない場合は、資料を整合させてから作問する。`generation_record`内の修正前表現、未承認・未判定・`unused`候補は承認済み表現の代わりに使わない。

### 分類ごとの辞書の使い方

- **C01〜C05:** `train`の承認済み終止形を基本に、対応する単独操作の問題を作る。`kより大きい`と`k以上`などの境界や、反転と降順の違いは`must_preserve_ja`に従う。
- **C06〜C09:** 操作ごとに`train`の承認済み接続形・終止形を選び、意味ASTの順序・回数を保って組み合わせる。表現ごとの承認を、組み合わせた全文の承認とは扱わない。全文にした際の修飾先や順序を改めてレビューする。
- **C10:** 承認済み`train`表現と意味仕様を参考に、Astraへ新しい言い回しを提案させる。冒頭や丁寧さだけを変えたものと、操作自体を新しい言い回しにしたものを区別する。「未学習の言い回し」として採用する10問は、操作表現について実際のBoku訓練指示との照合・意味レビューを通す。未確認の候補を未学習と断定しない。

C01〜C09に承認済みの学習用表現を使うことは許容し、その利用件数を報告する。全文が新しいこと、操作表現が未学習であること、意味ASTが未学習であることは別々に記録する。辞書を使っただけで全問を未学習問題とは説明しない。Qwenの学習コーパス全体との照合はできないため、ここでの未学習性は確認対象のBoku学習データに対するものとする。

### 既存テスト専用表現との分離

既存の`test_only`23件と辞書外9件は、既存30問の言い換え評価を維持するため、本ベンチマークのAstraへの参考例・few-shot例・開発問題・本番100問へ流用しない。終止形、接続形、表現IDをまとめて除外する。評価から除外済みの旧表記2件も再採用しない。これらの資料は作問後の照合用として管理し、Astraへ渡す参考辞書からは除く。

新規C10候補も既存テスト専用表現との一致を検査する。一致した候補は新規問題として採用せず、既存評価の表現を変更せずに別候補を作る。既存30問は比較の背景情報として報告できるが、100問へ足したり置き換えたりしない。

### Astraへ渡す資料

1. 24操作の意味仕様、参照インタプリタの仕様、CNL文法、関数契約`solve(xs, k)`。
2. 本書の10分類、操作数の制限、難易度、100点の採点規則。
3. 承認済みCSVから抽出した`train`522件の参考辞書。各行には表現ID、操作ID、意味AST、保持すべき意味、終止形、接続形、辞書区分を付ける。分割のない全545件や、生成時の未修正候補をそのまま渡さない。
4. 分類ごとに使う表現の方針、既存データとの重複検査条件、今回作るのが開発用か本番用かの指定。

参考辞書の抽出ファイル、元資料のhash、実際に渡した依頼文を保存する。既存テスト専用表現の本文・IDは依頼文に含めず、除外確認は作問側の検査で行う。参考辞書を渡す相手は問題作成役のAstraであり、比較対象のBokuやQwenへ辞書や正解を追加で渡すことはしない。

### 依頼文の要件

以下を依頼文の基本とし、開発用は各分類5問程度、本番用は各分類10問と明示する。

> Boku1-nanoの対象範囲である24操作・最大3操作から、指定された10分類のコード生成問題を作成してください。
>
> 添付する日本語表現辞書は、利用者が最終承認した辞書から、作問の参考に使えるtrain区分だけを抽出したものです。この辞書を必ず参照してください。各表現のoperation_id、operation_ast、canonical_meaning_ja、must_preserve_jaを読み、終止形と接続形の意味を保って使ってください。学習用表現を参照した問題を、未学習表現の問題とは呼ばないでください。
>
> C01〜C05は承認済みの単独操作表現を基本に作成し、C06〜C09は接続形と終止形を操作順に組み合わせてください。C10は承認済み表現の意味を基準に新しい言い回しを提案してください。新規表現や改変した表現は、利用者が承認済みの表現と区別し、候補として記録してください。
>
> 各問には自然な日本語、同じ意味のCNL、意味AST、分類、難易度、採点上の注意を付けてください。各操作に対して参考にしたexpression_id、実際に使用した表現、終止形・接続形の別、原文使用・改変・新規提案の別を記録してください。参考にした表現と、そのまま使った表現を混同しないでください。
>
> 問題はモデルの得点や勝敗を指定せず作成してください。操作順序・回数・数値条件が一意に決まり、既存仕様の範囲で正解を機械検証できる内容にしてください。すべての問題文はレビュー前の候補として出力し、承認済み辞書を参考にしたことを理由に、問題文まで承認済みと記録しないでください。

### 作問後の検査と採用

1. 表現IDを参考辞書へ照合し、操作ID・意味AST・終止形／接続形の対応を確認する。実使用表現が原文と異なる場合は`adapted`または`new`として扱う。
2. 日本語全文・CNL・意味ASTの操作数、順序、反復回数、kの条件、元順序を保持する条件が一致するかレビューする。参照コードと参照インタプリタの出力一致も確認する。
3. 元のルール生成指示だけでなく、教師言い換えを置換反映した実際の訓練指示と照合する。モデルごとに使用したデータ版を特定し、全文一致・近い表現・操作表現・ASTの既知／未知を別々に記録する。実データを確認できないものは未確認とする。
4. 本番と開発用の全文重複を除外する。C10では評価したい新規の操作表現も開発用と分ける。既知の単独操作や承認済みtrain表現の共用は記録して許容するが、既存テスト専用表現の混入は除く。
5. C10は未学習性の照合結果と日本語の意味レビューが揃った問題だけ採用する。問題文を修正した場合は、表現の来歴・意味・重複を再検査する。Astraが自ら付けた「承認済み」「未学習」という判定は根拠にしない。
6. 本番を固定する前に、分類別の辞書原文使用・改変・新規表現の件数と、参照した表現IDの分布を確認する。操作別の辞書件数の多さによって出題数が偏らないようにする。

Astraの出力はすべて候補として扱う。既知の単独操作を含むため、100問すべてを未学習の意味とは呼ばない。既存辞書の承認記録は書き換えず、新しい問題のレビュー記録を別途残す。

## 6. 比較条件

同じ100問について、以下の2条件を別々に集計する。条件Aを主比較、条件Bを補助評価とし、200点に合算しない。

| 条件 | Boku側 | Qwen側 | 解釈 |
| --- | --- | --- | --- |
| A: 日本語から直接生成・主評価 | 元の問題文を直接入力 | 同じ問題文からコードを生成 | 単体の入力理解とコード生成 |
| B: CNLから直接生成・補助評価 | 正解CNLを入力 | 同じ正解CNLからコードを生成 | 入力表現をそろえたコード生成 |

- 条件AのBoku入力はCNL検査を経由させない。現在のデモはCNL専用のため、評価用の直接入力経路を独立して用意する。
- 条件Bの正解CNLは人が検証した問題データを使用し、Qwenの変換結果を使わない。

### モデル・生成条件

- Bokuは`15m-1epoch`、既存BPE、重みとtokenizerのhashを固定する。
- Qwenは`web/qwen-manifest.json`にあるモデル、revision、q4f16、実行ライブラリを固定する。
- 両モデルはgreedy、1問につきコード1候補とする。最良候補の選択や採点後の再生成は行わない。
- Qwen直接生成のプロンプトは、関数名、引数、戻り値、対象範囲を伝える専用仕様にする。CNL変換用プロンプトを流用しない。
- Qwen直接生成はthinking無効を基本とし、反復ペナルティなどを含む設定を開発段階で確定・保存する。
- tokenizerが違うため「同じtoken上限」を公平性の根拠にしない。正常な回答に十分な上限を開発時に定め、モデルごとの値と打ち切り件数を報告する。Bokuの系列長上限256は維持する。
- Bokuの未知tokenや入力超過は記録し、個別問題だけ入力を書き換えない。仕様内の問題で起きた場合は対応能力の制限として集計する。
- 1M・5Mや3 epoch・10 epochは追加比較候補とし、主比較の結果と混在させない。

## 7. 採点と実行テスト

1問1点、100点満点。すべての実行テストに合格した問題だけ1点とし、部分点は付けない。正解コードとの文字列一致ではなく、返された整数リストの内容と順序を比較する。

テスト入力は既存仕様の定義域に従う。現行参照実装ではkは1〜10であるため、k=0や負のkを勝手に加えない。xsには許容範囲内で、空リスト、1要素、負数、ゼロ、重複値、昇順・降順・混在、kより短いリストを含める。固定seedのランダム入力も追加する。

境界値のテスト数、ランダム入力数、実行時間上限は開発時に決定して固定する。生成モデルへはhidden testや期待出力を渡さない。

### 既存検証器の適用確認

既存検証器は構文や関数呼び出しを制限する。Qwenが生成した意味的に正しい別解を不当に落とさないよう、開発時に許可構文・型注釈・関数契約を確認する。

- 両モデルに同じ評価契約を適用する。
- Markdownのコードフェンス除去などの抽出規則は事前に固定し、生の出力も保存する。
- 関数本体や操作内容を採点側で補修しない。
- 複数コード候補から正解を探す抽出は行わない。
- 検証器の許可範囲を超えた出力は、構文エラーや意味誤りと区別して記録する。
- 必要な検証器改修は本番前に両モデル共通で行う。無制限に生成コードを実行する変更は避ける。

失敗理由は、入力制限、コード抽出失敗、構文・契約不一致、実行エラー、時間超過、出力不一致、生成打ち切りに分ける。ブラウザ起動失敗などの基盤障害は問題の誤答と混同せず、同じ固定条件での再実行履歴を残す。

## 8. ブラウザ実行と記録

コード生成は同じ端末・ChromeまたはEdge・WebGPU環境で実行する。自動評価用画面またはブラウザ実行ハーネスから問題を順に投入し、出力を保存する。生成コードの採点は既存のPython検証基盤を使い、ブラウザ推論と採点場所を報告書に明記する。

QwenとBokuは原則として順番に読み込み、不要なモデルを解放する。片方だけWASMで測った結果を同じWebGPU比較として扱わない。

保存内容:

- 実行ID、問題セットのversion/hash、実行日時、端末・ブラウザ・GPU・backend。
- モデル・tokenizer・プロンプト・設定のversion/hash。
- 元の問題文、実際に渡したプロンプト、生の生成出力、採点対象コード。
- 問題ごとの合否と理由、生成token数、終了理由。
- 初回取得時間、キャッシュ後読込時間、生成時間。

速度の主指標はコード完成までの秒数とする。tokens/sはtokenizerの違いに左右されるため補助指標とし、モデルの読込を含む時間と含まない時間を分ける。
