## 1. 結論と推奨する順序

**現在の問題は「loopモデルが学習できない」ことではなく、「圧縮時に能力を維持できず、同容量でも追加計算に見合う優位が出ていない」ことである。**

- 0.426M・1層×3周・embedding共有は3 epochでも実行正解率21.8604%。通常1M・3 epochの99.5517%に大きく届かない。ただし、層削減・層共有・embedding共有を同時に変更しており、原因の分離が足りない。
- 1Mの中間層4回反復は3 epochで98.8244%まで学習できた。しかし通常1Mから615件の追加失敗があり、重み数も減らず、block適用回数は3回から6回になる。
- 残差倍率0.25は一部指標を改善したが、総合・構成汎化の優位を示していない。単純な入力加算や一律残差縮小も既に試されている。
- 反復処理、逆伝播、因果mask、教師ラベルに、大幅な不振を直接説明する重大な実装不具合は読み取り監査で見つからなかった。学習中の勾配競合や表現の均一化は未測定である。

次の順に進める。

1. **3 epochで欠けている対照を揃える。** 通常1層対1層×3周、embedding共有あり対なしを比較する。
2. **通常1Mの成功重みを利用する。** 学習済み重みからの初期化、教師の出力分布を用いた蒸留、周回別の小さな差分パラメータを順次比較する。
3. **全block共有を緩める。** 上記診断で共有が制約と示された場合、周回別LoRAまたはattentionのみ共有を試す。
4. **有望候補だけ追加学習・複数seed・独立評価へ進める。** 反復数、幅縮小、新しい学習目的を同時に増やさない。

## 2. 当初の方針と実験の到達点

### 2.1 当初は「圧縮」と「構成汎化」の二つを狙っていた

[導入方針](../policies/boku_nano_looped_transformer_plan.md)の主目的は、通常1M・3層・3 epochの能力を維持したまま1M未満へ圧縮することだった。主候補LT1は幅128・FFN256・1物理層×3周・embedding/head共有の426,368 parametersである。

これとは別に、反復構造が長い操作列の構成汎化に役立つという仮説があった。中間層4回反復は後者を調べる構成で、1,016,704 parametersのままなので圧縮成果とは扱わない。モデル内部の周回数と、生成するPythonの操作数は対応すると仮定しない。

元方針にはU3/U1/L1/T3/T1/LT1などの対照が計画されていたが、確認できた小型化報告では、その基礎比較より先に小型4系列の結果が出ている。また、方針§12の「修正4候補の本学習結果はまだない」は後続報告で更新済みの時点情報である。現在の判断には10月18日の追試まで含める。

## 3. 原因をどこまで特定できるか

| 原因候補 | 確度・根拠 | 解釈と必要な確認 |
|---|---|---|
| 独立層・幅・FFN容量の削減 | 小型化系列の低下は事実。原因内訳は未分離 | 1 blockを反復しても独立した3 blockと同じ関数を学べる保証はない。U1/L1、T1/LT1、U3/T3を比較する |
| 共有層に複数の役割を負わせる制約 | 文献と整合する仮説 | 日本語入力処理、操作合成、Python出力で必要な変換が異なる可能性。周回別勾配、部分共有、LoRAで検証 |
| 訓練量・最適化の不足 | 中間×4が3 epochで高精度に達することは事実 | 1 epochの低精度で表現能力の限界を断定しない。ただし3 epochへの変更は更新数と日程の両方を変えるため、epoch数だけの因果効果ではない |
| 残差・勾配の尺度変化 | 初期値の1 batchで確認、学習中の原因は未確定 | 初期normを揃えた修正も生成性能を改善しなかった。clip頻度、更新量、周回勾配を学習中に記録する |
| 入力情報の消失、表現の均一化 | 未確認 | 1問のattention比率では断定不可。同じ正解prefix・token位置で測定し、周回スキップ等の介入も行う |
| embedding/head共有の影響 | 未分離 | 入力と出力の役割差はあり得るが、tyingは一般に有効なこともある。T3/U3、T1/U1、LT1/L1の比較が先 |
| データ構成と小容量モデルの不一致 | データ分布は事実、loop特有の原因は仮説 | 3操作が95.26%、単独操作が0.24%。操作長別の誤りと教師コード形式の負担を調べる |
| 実装不具合 | 読み取り監査で主因は見つからず | 不具合不存在の証明ではない。特に今後の新構造では互換性・因果性・保存読込を再確認 |

### 3.1 誤りは構文だけの問題ではない

W64は構文・安全AST・signatureの通過率が93.9184%でも、実行正解率は0.1549%だった。LT1も同じ静的検査の通過率は97.8876%である。したがって、文法制約を付けるだけで今回の差が埋まるとは期待しにくい。操作選択、順序、前段結果の利用、引数kの扱いなどの意味的失敗を分類する必要がある。[小型4系列の生成健全性](boku_nano_looped_all_sizes_20261015.md)

### 3.2 初期normの増加と、学習失敗の原因は別である

[初期化診断](figures/looped_revision_diagnostics_20261016/initialization.json)では、同じ初期重み・実データ64例・CPU float32・更新前で、R=1/2/3の最終hidden RMSが0.02760/0.04339/0.06401、勾配normが3.340/5.331/6.701だった。

一方、[forward倍率診断](figures/looped_revision_diagnostics_20261016/forward_scale.json)でR=2の残差を0.5倍にすると初期勾配normは3.010まで下がるが、本学習の性能は改善していない。初期射影だけを縮小する方法も、hidden RMSの減少と勾配normの減少が一致しない。これらを根拠に「勾配爆発が主因」「1/Rで解決」と断定しない。

### 3.3 実装とログから確認したこと

- [モデル本体](../../scripts/model/boku_nano.py)は同一blockを再利用し、周回間で勾配を切っていない。各適用でQ/K/VとRoPEを計算し、causal maskを維持する。最終周回後のcode＋EOSにshifted CEを適用する。
- embedding/head共有は同一Parameterへの参照で、optimizerの二重登録をしていない。`add`も第1周には二重加算しない。残差射影初期化の`1/sqrt(2K)`は物理層数Kを使う意図的仕様で、Rを含まないこと自体をバグとは扱わない。
- [trainer](../../scripts/model/train_boku_nano.py)は毎更新のclip前normを計算するが、記録は通常20更新ごとのその時点の値。全期間のclip率や区間の最大値は既存ログから復元できない。
- 勾配蓄積はmicrobatchごとの平均CEを平均するため、教師token数が違う場合に`512×1`と`16×32`は厳密には等価でない。端数の蓄積窓にも注意が必要。ただし既報比較は`512×1`なので、これを既存不振の主因にしない。今後microbatchを変えるなら、蓄積窓の教師token総数での正規化と等価性確認を先に行う。

[共有・勾配のテスト定義](../../tests/test_looped_boku_nano.py)、[修正構造のテスト定義](../../tests/test_looped_boku_nano_revision.py)、[既存の32テスト等の検証記録](figures/looped_revision_diagnostics_20261016/implementation_verification.json)も確認した。今回これらのテストを再実行したという意味ではない。

## 4. 一次文献から採る方針と、その限界

2026-10-24時点で本文または会議版を確認した。論文の性能数値をBoku-nanoの期待改善幅へ換算しない。特に一般事前学習の大規模モデルと、幅128・少数周回・条件付きコード生成を区別する。

## 5. 改善実験の具体案

### 段階0: 成果物と診断を揃える

最新loop系列について、重みだけでなく、model/training config、データhash、tokenizer hash、学習ログ、suite別集計、問題別生成・採点結果を一緒に保存・復元する。復元できない系列は報告値との比較に留め、新しい実験名で再学習する。

診断には、評価の得点を見て選び直さない固定train/validation部分集合を用意する。単独・2操作・3操作、短い/長いコードを層別化し、以下を測る。

| 診断 | 測定方法 | 次の判断 |
|---|---|---|
| 小集合を学び切れるか | 例として固定train 512件でU3とL1/LT1を学習し、教師token lossとgreedy実行正解率を比較。上限更新数を事前固定 | train自体で大差なら最適化・容量を優先。train成功/dev失敗なら汎化を優先。ただし単独では原因確定しない |
| 共有勾配の競合 | 固定batchで重みを同値にした展開モデルを用い、周回別の勾配とその和、cosineを比較 | 競合が強ければLoRA・部分共有を優先 |
| 残差と更新の規模 | 毎更新clip件数、norm最大値・分位点、block別更新量/重み量。固定batchで周回別hidden RMSと相対更新 | 初期化だけの異常と学習中の問題を区別 |
| 反復が役に立つか | 同一gold prefix・同一位置で周回別状態を比較し、周回を省略したときの最終loss/実行精度を測る | 効果がない周回を増やさない。学習していない停止位置の悪化だけで無価値と断定しない |
| 意味的な誤り | 操作欠落、不要操作、順序違い、前段結果の不使用、kの誤用、EOS/上限到達を分類 | データ・構造の変更を誤りに対応づける |

中間状態へ最終headを当てたlossは診断値であり、その状態が出力用に学習されていない影響も受ける。attention比率や途中lossだけを原因の判定に使わない。

### 段階1: 3 epochの最小対照実験

幅128・FFN256・標準BPE2048・context256・AdamW・code＋EOS loss・microbatch512×蓄積1・データ順を揃える。全候補を最初から3 epoch、1,131更新の通常日程で学習する。既存基準に合わせLRは3e-4→3e-5、warmup5%（57更新）。これは1 epoch日程の延長案ではなく、成功済み3 epoch条件による構造比較である。

| variant | 構造 | embedding/head | parameters | 分離できること |
|---|---|---|---:|---|
| `u3` | 独立3層 | 非共有 | 1,016,704 | 同時再学習の基準 |
| `t3` | 独立3層 | 共有 | 754,560 | U3との差で語彙行列共有の影響 |
| `u1` | 通常1層 | 非共有 | 688,512 | 独立層を減らすだけの対照 |
| `l1` | 1層×3周 | 非共有 | 688,512 | U1との差で同容量の反復価値 |
| `t1` | 通常1層 | 共有 | 426,368 | LT1と同容量の対照 |
| `lt1` | 1層×3周 | 共有 | 426,368 | T1との差で反復価値、L1との差でtyingの影響 |

異なる物理層数では初期化の残差尺度も異なるため、U3対L1を「共有だけの違い」と説明しない。同じ構造のR比較では初期stateの一致を確認する。全条件で乱数seed、データ順、実際の教師token数・更新数を記録する。

**この6条件が最優先。** `t3`だけで能力維持できれば、約25.8%の圧縮を単純な構造で実現する候補になる。`t1`が`lt1`と同等以上なら、その容量でloopを選ぶ理由はない。`l1`が良く`lt1`が悪ければ、幅縮小に進む前にembedding共有を再検討する。

同容量での汎化改善も追う場合は、同runに`u3_middle4`を追加する。0.25倍は最初の必須条件にはしない。middle4が有望になった段階で、同じ幅・FFN・6回のblock適用を持つ通常6層（1,508,992 parameters）も別対照にする。これは同パラメータ対照ではなく、概ね同じblock計算量の対照である。厳密な計算・時間比較は実測する。

既存runnerで6条件を実行する例（**今回未実行**。リポジトリのルートで実行）：

```bash
uv run --python 3.12.12 --group model-training python \
  scripts/model/run_boku_nano_looped_experiment.py \
  --output-root data/models/looped_controls_3epoch_20261024 \
  --variants u3 t3 u1 l1 t1 lt1 \
  --epochs 3 --seed 20260925 \
  --device cuda --dtype bfloat16 \
  --micro-batch-size 512 --gradient-accumulation-steps 1 \
  --run --evaluate
```

出力先は未使用の名前にする。`--run --evaluate`は全5集合評価まで行うため、訓練だけより時間がかかる。試行数を増やす場合は、候補選定を専用devに寄せ、正式5集合を繰り返し最適化に使わない。

### 段階2: 成功済み通常モデルから共有モデルへ変換する

新規改善の第一候補は、通常1Mを凍結teacherとする変換・追加学習である。まずembedding/headを非共有のままにしたL1系で、層共有の回復だけを検証する。tied化や幅縮小を同時に加えない。

| 条件 | 前の条件からの変更 | 検証すること |
|---|---|---|
| A: ランダム初期化L1＋正解コードCE | 段階1の基準 | 共有モデルを一から学ぶ場合 |
| B: U3から初期化したL1＋CE | 初期重みのみ | 既学習の構文・意味知識が有効か |
| C: B＋teacher KL | 損失だけ | 教師の出力分布が回復を助けるか |
| D: C＋周回別LoRA | 共有の制約だけ | 周回ごとの役割差が必要か |

学生側の学習token数・更新数・日程はA〜Dで共通にし、初回は3 epoch相当で固定する。B〜Dは共有blockに加えてembedding、head、final normもU3から初期化する。teacherのみを凍結し、studentは共有重みを含む全パラメータを更新する。LoRA追加時もbaseを凍結する方式へ同時に変更しない。

**初期化方法は事前に固定する。** 厳密共有のBでは教師の各blockをコピーした候補をdevで比較するか、単一の選択規則を定める。層の単純平均が常に良いとは仮定しない。LoRA版では共有重みと教師各層との差を低rankで近似する方法が文献にあるが、その場合はLoRAなしの対照も同じ共有初期値で再評価する。[Bae et al. §3.4–3.5](https://arxiv.org/html/2410.20672v2)

蒸留は訓練集合の**同じ正解prefix、code＋EOS位置だけ**で行う。正解コードのCEを残し、`L = (1−α) CE + α T² KL(p_teacher,T || p_student,T)`を比較する。例としてα=0.5、T=1から始めるが、この数値はBoku-nano向けの仮置きであり論文の保証値ではない。teacherの言い換え15/30という弱点まで模倣し得るので、gold教師を置き換えない。

LoRAは例としてrank4の小さな条件から始め、実パラメータ数と保存bytesを再計算する。追加した周回固有重みを含めて圧縮率を報告する。ランダム初期化＋CE＋LoRAの対照も有望段階で加え、利益が単なる追加容量かを調べる。teacherの事前訓練費用・teacher forward・追加学習費用は、学生単体の訓練費用と分けて報告する。

これらの変換・蒸留・LoRA機能は現runnerでは未実装。現在の`--resume-from`は異なるモデル構造への変換を拒否するので、通常resumeを流用せず、由来hashを残す別の変換処理が必要である。

### 段階3: 共有範囲と訓練データを、診断結果に応じて変更する

| 優先条件 | 改善案 | 対照・制約 |
|---|---|---|
| 周回の役割競合が疑われる | attentionを共有し、FFNを周回ごとに独立にする | ALBERTを根拠とする仮説。LoRAとの同時投入を避ける。単純な全共有・同程度容量の通常モデルと比較 |
| 3 epoch末でもtrain/devが改善中 | 有望候補と通常対照の両方を、最初から6 epoch設定で再比較 | 追加学習は条件付き。3 epoch後の低いLRをそのまま延ばすresumeと混同しない。6 epochでも未達なら無制限に延長しない |
| 構造比較後も更新が弱い/clipが偏る | 3 epoch条件でpeak LRを例として1.5e-4/3e-4/6e-4の3点比較 | warmup・減衰形状を固定し、通常版にも同じ探索予算を与える。1 epochの減衰延長は対象外 |
| 単独操作・表現転用で失敗が集中 | 操作数の層別sampling、または教師Python表現の正規化 | 元の3操作中心分布との差を記録。同じデータ変更を通常版にも適用。2案を同時導入しない |
| 同じ入力情報を反復で失う証拠がある | prelude表現を介したgate/adapter付き注入 | 生embeddingの単純加算とは別案。入力介入診断後に限定。追加パラメータと計算を計上 |

訓練分布は単独460件、2操作8,680件、3操作183,760件である。[最終訓練データ報告](final_train_dataset_results.md) 同じ意味ASTに複数のコード表現を持つことが、小容量モデルに表面形式の学習負担を与える可能性はある。ただし、同一promptに矛盾する教師があるとは確認していない。正規化を試す場合も、機能的に同じ別コードを評価で誤答扱いしない。

**現時点で優先しないもの:** 幅64/96への追加圧縮、単純な周回数増加、学習していない周回数での性能向上を前提とする運用、中間周回lossの一括導入、ACT、truncated BPTT、MNTP/DWA等の同時追加。どれも原理的に否定するのではなく、現状の原因分離に対する追加要因が多い。特に中間lossは最終出力性能を損ねる先行例があり、自動的な改善策にはしない。[Bae et al. Appendix J](https://arxiv.org/html/2410.20672v2)

## 6. 評価・採用・打ち切りのルール

### 6.1 二つの目的ごとに判定する

**圧縮系列:** 旧方針の暫定基準を引き継ぐ。再学習したU3に対して固定5集合のmicro低下0.05 percentage points以内、通常・組合せ・反復・境界の各低下0.10 points以内、言い換えの正解件数を減らさない。872問では全カテゴリを報告し、候補採用では各カテゴリの正解数維持を求める。基準を得点の後で広げない。**10/25更新:** v2は使わず、発表資料の固定872問・179入力・旧採点器で同条件評価したU3を基準とする。

**同容量の汎化系列:** 事前に主対象を4操作・ABAB等の専用dev/finalとして固定し、通常モデルからの対応差を示す。正式5集合の能力退行も同時に報告する。重みが減らず推論が遅くなる場合、微小な全体差だけでは採用しない。既存middle4は圧縮系列の品質閾値も満たしていない。

閾値は工学上の候補選定基準であり、統計的な非劣性の証明ではない。最初は共通1 seedで候補を絞り、最終候補・浅い同容量対照・U3を合計3 seed以上で対応比較する。seed別値、平均、差の不確実性を報告する。

### 6.2 評価の独立性と計算費用

- 固定5集合、言い換え30件、dev50、固定872問は既に開発に参照されている。新しい汎化主張には、操作列・意味AST・機能等価群を考慮して未使用の確認集合を凍結する。訓練分割そのものを変える場合は通常版も再学習する。
- normal/boundaryの重複や同一ASTの表現違いを独立標本として扱わない。モデル間は同じ問題を対応づけ、AST/操作列単位の再標本化などで差の不確実性を見る。
- 言い換えの1件差は3.33 points。小集合は正解数と改善/退行した問題を併記し、84,550件の平均に埋めない。
- 同データ量比較と同計算予算比較を分ける。層適用回数は概算であり、embedding/head・生成長・実装の費用を含む正確なFLOPs/時間ではない。
- 配布bytes、ONNX bytes、固定prefix長での時間、実生成時間、tokens/s、peak memoryを同一端末・dtypeで測る。学習時間と、84,550問の生成・検証時間も分けて記録する。

### 6.3 次段階へ進まない条件

1. T1に対しLT1が複数seedで品質・用途上の利益を示さなければ、その容量ではloop採用を見送る。
2. 初期化・蒸留・共有緩和でも品質基準に届かなければ、幅縮小や反復追加へ進まず、より緩い圧縮候補T3/T2や通常モデルを選択肢に戻す。T2は590,464 parametersである。
3. 3 epochで共有効果を分離できる前に、データ変更と構造変更を同時に投入しない。
4. 追加学習でtrain lossだけ下がり、専用devの意味的正解率が改善しなければ、その方向の計算追加を止める。
